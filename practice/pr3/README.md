# ПР3. ACK, тайм-ауты, повторная передача

**Ветка:** `feature/reliable-delivery`. Документы: `docs/Reliability_Protocol.md`, `docs/reliability_samples.csv`.

## Адаптация
| Игра | Nomi |
|---|---|
| SHOOT надёжный | **CHAT** (сообщения и кружки) надёжные, `requiresAck=1` |
| MOVEMENT ненадёжный | **POSITION** ненадёжный: новая позиция заменяет старую |
| REACTION | ненадёжный (безопасно потерять) |

## Реализация
- `shared/reliability.mjs`: `ReliableChannel` (без сокетов: `onSent`, `onAck`, `collect`, `drainFailed`), `AdaptiveTimeout` (`RTO = SRTT + 4·RTTVAR`, 100–3000 мс), экспоненциальная задержка `RTO·2^(attempt−1)`.
- Сервер: на пакет с `requiresAck` сразу отправляет `ACK`, окно из 256 номеров защищает от повторного эффекта (сообщение не дублируется).
- Клиент: цикл раз в 100 мс вызывает `collect`; после 5 попыток в чате стоит ✗, показывается уведомление.
- Алгоритм Карна: RTT от ACK пересланного пакета в оценку не берётся.

Приватные диалоги: `ACK` означает «принято сервером» (✓), а не «прочитано адресатом». Сообщение адресату сервер отправляет по уже открытому каналу.

## Проверка
`http://localhost:3000/?loss=0.2` — отправьте сообщения, галочки ✓ появляются с задержкой, `/stats` показывает `dupes`.
`npm test` — повтор по RTO, дубль ACK, исчерпание попыток.

## Эксперимент (6 серий × 50 сообщений)
`baseline`, `loss_5`, `loss_10`, `loss_20`, `delay_100_loss_5`, `jitter_loss_10`. Нужны: среднее число попыток, доля с 1-й попытки, failed, время до ACK, RTO в конце. Логирование в CSV добавьте в обработчик ACK.

## Защита
- **ACK на ACK?** Не нужен: ACK не имеет `requiresAck`.
- **Что при окончательной недоставке?** Пользователь видит ✗ и может отправить заново.
- **Почему позиции ненадёжные?** Старая позиция бесполезна, когда пришла новая.
